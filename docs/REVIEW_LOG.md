## Round 66 — Financial architecture review & adversarial QA (independent verification)
**Trigger:** owner task — independently review and stress-test the `eea4bb7` financial foundation; verification + targeted repair only; no production DB modifications; migration NOT applied by this round.
**Method:** every claim re-derived from actual code (ledger.ts, deals.ts, domain.ts, finance/*, migration SQL, admin finance overview, webhook route, action route, reconciliation) — not from the prior completion report. All 20 mandated scenario families re-executed through the real HTTP surface on an isolated PGlite (real Postgres semantics) rig, plus a new adversarial block.
**Defects found and fixed (6 code + 2 machine edges):**
1. **Concurrent money race on Postgres** — `applyTransition` wrote status unconditionally; two concurrent settlements/refunds/fundings under READ COMMITTED could both post (instruction dedupe does not serialise them; SQLite rigs masked it). Fix: compare-and-swap status write (`updateMany` validated-status predicate, zero rows ⇒ `ConcurrentDealUpdateError` 409, whole tx incl. ledger rolls back). Regression R11: exactly one of two concurrent settles succeeds, landlord paid exactly once.
2. **Deposit custody flag never enforced** — `deposit_custody_provider_confirmed` (default false) was display-only; live-mode funding collected the deposit as a real custody claim. Fix: fail-closed gate (`DepositCustodyUnconfirmedError` 409) in BOTH the fund action and the webhook booking path; sandbox rehearsal unaffected; deposit-free funding unaffected. (Live-mode behaviour is env-gated and not rig-exercisable; reported as such.)
3. **`applyDeduction` posted without re-checking the held balance in the posting tx** (check ran in an earlier tx, before the PSP instruction) — an interleaved release/refund could drive `deposit_liability` negative. Fix: balance re-read inside the posting transaction.
4. **Stacked pending deposit releases** — repeated `refund-deposit` created multiple full-balance pending records (double provider instruction risk at go-live). Fix: one pending deposit release per deal (`RELEASE_ALREADY_PENDING` 409); completion-time ledger balance check remains the hard guard.
5. **Action catalogue ≠ handlers for the verification window** — `confirm-move-in-landlord` was offered in states where it 409s and hidden in the one state where it works (dual-confirm completion invisible); `add-move-in-evidence` likewise hidden while a verification was open, contradicting its own docstring. Fix: `to:null + offeredIn:['move_in_awaiting_verification']` and `alsoReachableFrom` += awaiting; machine untouched.
6. **Verification state labels swapped** — tenant's second confirm wrote `landlord_confirmed` and vice-versa (audit/UI mislabel; finance overview counts open verifications by state). Fix: literals corrected to the "latest confirmer" convention.
7. **Re-opening a decided handover hit the DB unique constraint** — after a NOT-verified review decision, tenant confirm tried to re-create the verification row → raw P2002/500. Fix: explicit 409 `MOVEIN_DECISION_FINAL` (the decision is final; only a refund releases the money).
8. **`move_in_disputed` could not reach `reversed`** while the reversal handler listed it as reversible (handler/machine disagreement; the request died in the machine check). Fix: additive `reversed` edge; regression R9 (reversal from a disputed deal zeroes custody+commission).
**Adversarials verified clean (no fix needed):** commission once-only (CAS now also guards the legacy earn step), deposit excluded from commission base, renewal has no commission path, fees borne by HFR never touch tenant/deposit, duplicate webhooks cannot double-book (terminal-state refusal + money guard + duplicate-collect audit), partial refunds bounded inside the completion tx, post-settlement refund is a landlord coordination (no platform balance, no false receipt, refusal→escalated terminal), duplicate-payment refunds stay honestly pending (no completion invented), reconciliation stays green across all adversarial paths.
**New regressions:** R1–R11 block in `scripts/finance-pipeline-tests.mjs` — suite now **125/125 ALL PASS** (was 89); tsc 0; ESLint 0.
**Migration review:** additive-only re-confirmed (7 enums + 11 enum values + 1 nullable listing column + 6 nullable deal columns + 6 new tables/FKs/indexes; no UPDATE/DELETE/ALTER of existing columns; immutability triggers untouched; `move_in_verification.deal_id` and `deposit_case.deal_id` uniques match the code's findUnique usage). NOT applied by this round; rollback: tables/columns droppable, Postgres enum values are NOT droppable in place (recreate-enum caveat).

## Phase 2 review round (2026-10-31) — financial operations completion

**Defects found by this round's own adversarial pass (all fixed + regression-tested):**
1. **Live-mode payout instruction dedupe attached a second refund record's payout to the first record's instruction** (dedupe was `(dealId, kind)`; two refund records → one provider payout, wrong amounts). Fix: dedupe per idempotency key (the purpose); regression P2-B counts instructions before/after a retry.
2. **A provider-reported payout failure only marked refund records failed when the deal was parked in `refund_pending`** — duplicate-payment refunds (which never park the deal) would have stayed pending forever. Fix: mark linked pending records failed before the deal-status branches; regression P2-B failure path.
3. **The webhook's generic refund fallback could dispatch a duplicate_payment record into `applyRefundCompletion`** (a rent-liability posting for money that was never a booked liability) or wedge the webhook in a retry loop after a terminal transition. Fix: ONE shared `completeRefundRecordByKind` dispatcher for the webhook AND the retry path, with decided-record idempotency; regression P2-B redelivery.
4. **`duplicatePaymentRefund` had no cumulative bound** — repeated records for one extra collection could each instruct a payout up to the full collected amount. Fix: pending+confirmed duplicate refunds can never total more than was collected (`DUPLICATE_REFUND_EXCEEDS_COLLECTION`); regressions P2-A bound triple.
5. **Reconciliation's payout mirror would have flagged duplicate-payment payouts as a PSP/ledger mismatch** (they deliberately book nothing). Fix: explicit, documented exclusion by refund-record kind — the mirror loosens nothing on the ledger side; suite 18 stays green with duplicates present.
6. **Statement classification order was UUID-lucky** (which provider line "first matched" a reference and which was the duplicate). Fix: `line_seq` import-order column drives deterministic classification; regression P2-C asserts the duplicate verdict lands on the second row.
7. **Failed payout instructions could have booked money** in the mock-park paths (`settle`/`refund`/`partialRefund`/`refundDeposit`/`reverseCommission` treated non-pending as success). Fix: every payout path refuses on a failed instruction (502 `PSP_INSTRUCTION_FAILED`, record marked failed, nothing booked).
8. **Live release/refund instructions were issued without a provider reference**, making them permanently unmatchable by statements. Fix: UUID provider reference at issue time.
